# ИНСТРУКЦИЯ ПО ПРИМЕНЕНИЮ — Universal Orchestrator Kit

Kit version: 1.0.0 · Spec version: 1.0.0 · Обновлено: 2026-11-17

Практическое руководство на русском языке: как проверить, установить и
использовать кит в своём проекте. Нормативные документы кита — на английском
(для переносимости между агентами); это руководство — навигация и порядок
действий для человека. При расхождении приоритет у нормативных документов
([UNIVERSAL-ORCHESTRATION-SPEC.md](UNIVERSAL-ORCHESTRATION-SPEC.md)).

---

## 1. Что это такое

Кит — переносимый стандарт оркестрации AI-агентов и моделей: политика
маршрутизации задач, 11 ролей агентов, жизненный цикл задачи, изоляция
проектов, шлюзы безопасности и качества, исполняемое эталонное ядро и
тесты. Он НЕ работающий сервис: «установить кит» значит внедрить его адаптер
в вашу среду (Claude Code, Qoder, Cursor, Codex или другую) и честно
зафиксировать, что реально работает.

Три слоя:

- **Слой A — универсальное ядро** (`core/`, `protocols/`): правила, не
  зависящие от приложения.
- **Слой B — адаптеры** (`adapters/`): перевод правил в нативные механизмы
  конкретной среды (субагенты, хуки, правила, модели).
- **Слой C — исполнение**: реальные агенты/модели/инструменты вашей среды.

## 2. Требования

- Python ≥ 3.10 и PyYAML (`pip install pyyaml`) — для тестов и установщиков.
- Целевая среда: Claude Code, Qoder, Cursor, Codex CLI или любой агент,
  умеющий читать файлы и выполнять команды (универсальный профиль).
- Сеть и ключи API для самих тестов НЕ нужны.

## 3. Шаг 1 — проверка кита (до установки)

```bash
cd UNIVERSAL-ORCHESTRATOR-KIT
python3 validation/self_test.py        # 16 структурных проверок CHK-01…16
python3 validation/behavior_tests.py   # 51 поведенческая проверка TS-01…12
python3 adapters/shared/hooks/test_g1_guard.py   # 123 теста хука G1
python3 adapters/shared/test_install_skill.py    # 5 тестов скилла-ярлыка установщиков
python3 adapters/shared/test_uok_cli.py          # 11 тестов CLI uok (init + bootstrap)
```

Все пять команд должны завершиться с кодом 0. Если PyYAML недоступен —
тесты считаются `not_executed`, а не «пройдены». После ЛЮБОГО изменения кита
перезапускайте все пять наборов.

## 4. Шаг 2 — установка в проект

**Первичный путь — `uok init` в сессии проекта.** Один раз на машину
зарегистрируйте глобальный скилл `uok-init` (он действует во всех проектах):

```bash
python3 UNIVERSAL-ORCHESTRATOR-KIT/uok bootstrap            # среды с конфигами в ~
python3 UNIVERSAL-ORCHESTRATOR-KIT/uok bootstrap --host all # или все четыре сразу
```

Bootstrap создаёт пользовательский скилл `uok-init` (`~/.claude/skills/`,
`~/.qoder/skills/`, `~/.cursor/skills/`, `~/.agents/skills/` — пути проверены
по официальной документации). Ваши собственные скиллы не перезаписываются.

После перезапуска сессии откройте любой проект и напишите в агентском чате:

```text
uok init
```

(или явно `/uok-init`; в Codex — `$uok-init`). Агент покажет план
(`--dry-run`), выполнит установку, честно отчитается о проверках и попросит
перезапустить сессию. Дальше задачи ставятся через `/uok <задача>` (§6.1).

Тот же CLI работает и в терминале:

```bash
python3 UNIVERSAL-ORCHESTRATOR-KIT/uok init --host qoder --project /path/to/project \
    --models tier1=lite,tier2=efficient,tier3=performance,review=performance
```

`--host auto` (по умолчанию) определяет среду эвристически (переменные
окружения → каталоги конфигов проекта → каталоги в ~); при неоднозначности
попросит указать `--host` явно. Скилл в сессии всегда передаёт `--host` сам.

**Запасной путь — прямой вызов установщика** (то же самое, что делает init):

Установщики аддитивны и идемпотентны: существующие конфиги сохраняются,
резервные копии кладутся в `.orchestrator/backups/<timestamp>/`.

```bash
# из корня проекта (кит лежит рядом или внутри):
python3 UNIVERSAL-ORCHESTRATOR-KIT/adapters/qoder/install.py --dry-run   # сначала просмотр
python3 UNIVERSAL-ORCHESTRATOR-KIT/adapters/qoder/install.py \
    --models tier1=lite,tier2=efficient,tier3=performance,review=performance
```

Замените `qoder` на `claude-code`, `cursor` или `codex` по вашей среде.

Флаги (одинаковы у всех установщиков):

- `--project DIR` — корень проекта (по умолчанию — родитель каталога кита);
- `--mode standard|strict` — strict дополнительно ограничивает shell воркеров
  allowlist'ом и запрещает перенаправления/подстановки;
- `--models tier1=…,tier2=…,tier3=…,review=…` — реальные селекторы моделей
  ВАШЕГО аккаунта. Установщик их не проверяет: передавайте то, что видите в
  интерфейсе среды;
- `--dry-run` — показать изменения без записи.

Что создаётся:

- `.orchestrator/` — рабочее дерево: `policy/` (project.yaml, models.yaml,
  agents.yaml), `tasks/`, `audit/`, `claims/`, `hooks/g1_guard.py`;
- нативные субагенты `uok-<роль>` (10 ролей; оркестратор — главная сессия);
- скилл-ярлык `uok` для запуска оркестрации (`/uok <задача>`; в Codex — `$uok`,
  подробнее в §6.1);
- помеченная секция UOK в файле инструкций (`CLAUDE.md` / `AGENTS.md`);
- PreToolUse-хук G1 в настройках среды (сливается с существующими хуками).

**После установки перезапустите сессию агента** — реестры субагентов обычно
загружаются при старте. Затем выполните живые проверки: для Qoder/Cursor/Codex
вставьте промпт из [handoff/LIVE-CHECKS.md](handoff/LIVE-CHECKS.md) в чат
соответствующего приложения. Результат оформите отчётом по
[шаблону](handoff/INSTALLATION-REPORT-TEMPLATE.md).

Для сред без установщика: агент выполняет
[AUTONOMOUS-IMPLEMENTATION-DIRECTIVE.md](AUTONOMOUS-IMPLEMENTATION-DIRECTIVE.md)
(13 шагов) с запасным профилем [adapters/universal/README.md](adapters/universal/README.md).

## 5. Шаг 3 — человеческая проверка хука G1

Хук G1 — единственный программный барьер между воркерами и опасными
действиями. Перед доверием ему пройдите
[handoff/HUMAN-REVIEW-G1.md](handoff/HUMAN-REVIEW-G1.md): просмотр кода,
проверка deny/ask/allow на синтетических событиях, запись результата.

Что делает G1 (кратко):

- запрещает чтение секретных путей (`.env`, ключи и т.п.) и секретоподобное
  содержимое в записях;
- запрещает запись вне заявленных ресурсных claims задачи (LC-04);
- защищает конфиги среды, `.orchestrator/`, файл инструкций и сам кит от
  записи воркерами;
- чувствительные операции (`git push --force` и т.п.) переводит в `ask` —
  решение принимает человек;
- в strict-режиме ограничивает shell воркеров allowlist'ом.

## 6. Повседневная работа

### 6.1 Как ставить задачи

Главная сессия агента — **оркестратор**. Формулируйте задачу обычным языком;
оркестратор обязан провести её по жизненному циклу:

```
RECEIVED → ANALYZED → CLASSIFIED → DECOMPOSED → DEPENDENCIES_RESOLVED
→ ROUTED → APPROVED_IF_REQUIRED → EXECUTING → VALIDATING
→ COMPLETED / FAILED / ESCALATED
```

**Быстрый запуск — скилл-ярлык `/uok`.** Установщик создаёт его автоматически:

| Среда | Файл скилла | Вызов |
|---|---|---|
| Claude Code | `.claude/skills/uok/SKILL.md` | `/uok <задача>` |
| Qoder | `.qoder/skills/uok/SKILL.md` | `/uok <задача>` |
| Cursor | `.cursor/skills/uok/SKILL.md` | `/uok` + задача в том же сообщении |
| Codex | `.agents/skills/uok/SKILL.md` | `$uok` + задача в том же сообщении (не slash) |

Пример:

> `/uok Разберись, как устроен модуль X (только чтение), затем исправь Y
> в `src/y/*` и проведи независимую проверку. Отчёт — с выводом тестов.`

Скилл разворачивает промпт оркестратора и проводит задачу по тому же циклу
(классификация → маршрутизация → claims → одобрения → проверка → отчёт
с доказательствами). В Claude Code скилл помечен `disable-model-invocation:
true` — запускается только человеком; `$ARGUMENTS` подставляет текст задачи.
В Cursor и Codex аргументы в файл скилла не подставляются — пишите задачу
в том же сообщении. Если имя `uok` уже занято вашим скиллом, установщик
его не трогает и сообщает об этом. После установки перезапустите сессию.

Можно и без скилла — обычным поручением:

> «Используй uok-research-analyst, чтобы разобраться, как устроен модуль X
> (только чтение). Затем uok-implementation-engineer пусть исправит Y,
> заявив claims на `src/y/*`. После этого uok-code-reviewer делает
> независимую проверку. Отчёт — с доказательствами (вывод тестов).»

### 6.2 Роли и маршрутизация

11 ролей (`core/AGENT-CAPABILITIES.yaml`): orchestrator, architect,
senior_engineer, implementation_engineer, research_analyst,
debugging_specialist, test_engineer, security_reviewer, code_reviewer,
documentation_specialist, release_integration. Роль ≠ модель: одна модель
может играть несколько ролей.

Маршрутизация детерминирована (`core/ROUTING-POLICY.md` + `routing-policy.yaml`):
категория задачи (CAT-01…08) → базовый тир → модификаторы сложности/рассуждения/
цены ошибки (потолок TIER-3) → жёсткие полы (архитектура и безопасность ≥ TIER-3,
специализированные ≥ TIER-4) → фильтр возможностей → ранжирование
(надёжность ↓, цена ↑, задержка, id). TIER-5 — только независимая проверка.
Исчерпание кандидатов → эскалация человеку, никогда тихая подмена слабой моделью.

### 6.3 Конфигурация проекта

После установки редактируйте `.orchestrator/policy/`:

- `project.yaml` — изоляция, чувствительные операции, shell-allowlist,
  параллелизм, бюджет;
- `models.yaml` — реальные модели: доступность, контекст, цены. Заполняйте
  ТОЛЬКО проверенными данными (страница цен провайдера, пробы), каждое
  значение — с `evidence` и `verified_at`. Неизвестное оставляйте `unknown`;
- `agents.yaml` — роли, инструменты, тиры. Независимость ревьюера
  (другая модель/инстанс) неудаляема.

Шаблоны с комментариями: [templates/](templates/). Значения по умолчанию
консервативны: строгая изоляция, авто-одобрение выключено, все шесть
чувствительных операций под шлюзом.

### 6.4 Одобрения (человек обязателен)

Явное одобрение человека требуется для: production-деплоя, финансовых
операций, необратимого изменения данных, разрушительных изменений
инфраструктуры, изменения доступов/учётных данных, неавторизованных внешних
публикаций. Плюс CAT-07 (безопасность) с любой записью.

Одобрение — запись `approval_record` (protocols/TASK-CONTRACT.md): конкретная
задача, конкретные операции, имя человека, срок действия. Пустой список
операций не одобряет ничего; истёкшее одобрение недействительно и при
исполнении, и при финальной приёмке (G4).

### 6.5 Параллельная работа

Параллельны только задачи без зависимостей и с совместимыми ресурсными
claims: write–write и write–read пересечения блокируются (реестр claims в
`.orchestrator/claims/`). Стратегии: реестр блокировок (по умолчанию),
git-worktree на каждого писателя, координация слияний ролью
release_integration. Нет безопасной стратегии — задачи сериализуются, и это
фиксируется в отчёте.

### 6.6 Изоляция проектов

Каждая задача принадлежит одному проекту и получает минимальный контекст
(context envelope). Межпроектный доступ — только по явному grant'у с
областью (конкретные пути, не весь проект), сроком и причиной; grant
действителен ТОЛЬКО из реестра получателя, не из самого конверта. Секреты
не передаются никогда — редакция перед каждой передачей.

### 6.7 Отказы, waivers, приёмка

- Циклы зависимостей отклоняются на DECOMPOSED.
- Незавершённая зависимость, провал дочерней задачи, отсутствие ревью —
  блокируют приёмку. Обойти можно ТОЛЬКО явным человеческим waiver'ом
  (`dependency`, `partial_acceptance`, `review`) с именем и сроком; waiver
  не может отключить изоляцию, редакцию секретов или список чувствительных
  операций.
- COMPLETED требует результата с доказательствами; для задач с высоким
  влиянием/безопасности — вердикт независимого ревью G3 с доказательствами.

## 7. Качество и улучшение политики

Метрики (core/QUALITY-GATES.md): доля завершённых, успех с первого раза,
частота ретраев, провалы валидации, время, токены, оценка стоимости,
надёжность моделей/ролей, частота вмешательства человека, регрессии.
Улучшения политики — только версионированные, аудируемые, обратимые
предложения по измеренным результатам; тихо переписывать ядро или ослаблять
шлюзы запрещено.

## 8. Если среда без нативной поддержки

Универсальный профиль (`adapters/universal/README.md`): ролевые сессии в
одном агенте, реестр claims оркестратором, headless CLI / внешние API /
ручной режим по лестнице деградации. Решения о деградации помечаются флагами
(`degraded_multi_agent`, `degraded_parallelism`, `degraded_model_routing`,
`doc_only_verification`) и попадает в отчёт установки. Каждое решение о
деградации фиксируется явно.

## 9. Границы честности

- Все утверждения о возможностях сред несут статус проверки: `unknown` /
  `unverified` / `verified_doc` / `verified_local` / `verified_live`.
  Документация ≠ работающая интеграция.
- Записи реальных моделей в реестре — иллюстрации (`example: true`,
  `availability: unverified`, цены `unknown`). Тестовые mock-модели
  (`test_only: true`) используются только тестами.
- Никогда не объявляйте тест пройденным, если он не запускался; никогда не
  выдавайте план за реализацию.
